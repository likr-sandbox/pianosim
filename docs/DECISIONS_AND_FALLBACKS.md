## D1：Web単一スレッド `AudioWorklet` ＋ 全約2.6万モード常時固定駆動

1. **現在の採用判断**: `COOP/COEP` ヘッダ不要で静的ホスティングでもそのまま動作する単一スレッド `AudioWorklet` ＋ `wasm32` SIMD128（`f32x4`）を採用し、品質プロファイル切替や休止弦スリープ間引きを行わず全88鍵・230本・約2.6万モードを毎サンプル常時固定駆動する。
2. **今回見送った選択肢**:
   - ① 品質プロファイル切替（`Ultra / Standard / Eco`）によるモード上限変更
   - ② エネルギー閾値による休止弦ブロック単位スリープ制御
   - ③ `SharedArrayBuffer` ＋ Web Worker マルチスレッドWasm並列化（静的ホストでの `coi-serviceworker` によるCOOP/COEPヘッダ注入）
3. **不採用とした理由**: ハイエンドPC環境における純粋フル物理演算の一貫性・最小構成・静的ホスティング互換性を優先し、品質差やスレッド同期オーバーヘッドを排した。
4. **判断誤りの検知シグナル**:
   - M2 / M6 / M8 のブラウザ検証において、128サンプル量子（48 kHzで `2.67 ms`、96 kHzで `1.33 ms`）に対する `AudioWorklet` の **p99処理時間が予算の70%（48 kHz時 約 `1.87 ms`）を超過**、またはオーディオアンダーラン（xrun）が発生した場合。
   - ノートPC省電力モードやモバイル端末への対応が必要となった場合。
5. **事前仕込みとリカバリ移行手順**:
   - **事前仕込み**: `piano-strings::modal_soa` は設計当初から4モード単位（`F32x4` 境界）かつ弦単位レンジ境界を整列して配置する。
   - **第1段階フォールバック（COOP/COEP不要）**: ダンパー接触中かつモードエネルギー包絡 `< -110 dB` かつ共通ブリッジ力 $|F_{\text{bridge}}|$ がノイズフロア以下の弦SIMDブロック更新をスキップするスリープ制御（カシオ特許 `JP7400925B2` の「倍音関係判定」は一切用いず純粋な物理エネルギー閾値のみ使用）および高次モード上限インデックス制御を導入する（ペダル解放時の演算量を最大80〜90%削減可能）。
   - **第2段階フォールバック（マルチコア解放）**: `apps/web` に `coi-serviceworker` を追加してCOOP/COEPを有効化し、Wasm Threads によって230本の弦SoAレンジを複数Workerへ分割並列化する。

## D2：純Rustオフライン物理シミュレーションによるプリセット・IR手続き生成

1. **現在の採用判断**: 実機録音データからの逆問題同定（Python/JAX）は行わず、Rust製のオフライン物理シミュレーションクレート（`piano-body-gen` / `piano-spec`）から全88鍵・230本の弦／ハンマー定数および構造音響モードを手続き生成する。
2. **今回見送った選択肢**: 共有レポート第1層にある Python/JAX（GPU並列）を用いた実機マルチ録音・MAESTROデータセットおよび実機ブリッジIRからの Matrix Pencil ＋ 複素対角SSM ＋ Spectral Optimal Transport 損失（$L_{\text{sot}}$）による微分可能パラメータ自動整音基盤。
3. **不採用とした理由**: 外部実機録音セットが存在しない前提で、純Rustモノレポのみでビルド・テスト・検証までを自己完結させるため。
4. **判断誤りの検知シグナル**: M6 / M8 の聴覚評価において、手続き生成した異方性板・リム・空気室モードや弦スケーリング則だけでは実在コンサートグランド特有のフォルマントの癖・個体差・鳴りムラが再現しきれず、均質・人工的な印象にとどまる場合。
5. **事前仕込みとリカバリ移行手順**:
   - **事前仕込み**: `piano-spec::preset_codec` を生成手段に依存しない独立の「極・留数＋弦／ハンマー物理定数バイナリ形式」として設計する。
   - **移行手順**: ランタイムDSP（Stage 1〜4）を一切変更することなく、リポジトリ外部または `tools/calibration-jax/` として自動微分キャリブレーションパイプラインを追加し、同定済みプリセットバイナリを差し替え投入する。

## D3：ビルド時構造モード同梱＋初期化時サンプルレート適応IR動的合成

1. **現在の採用判断**: ビルド時に `piano-body-gen` で1,000〜2,000個の構造モード（極・留数、数百KB）を算出し同梱。エンジン初期化時・聴取視点／大屋根変更時にホストの `AudioContext.sampleRate`（44.1 / 48 / 96 kHz）に合わせて9ゾーン×L/R（18経路、0.5秒IR）を数十msで動的合成する。
2. **今回見送った選択肢**:
   - ① 48 kHz基準の長尺IR波形バイナリ（数MB〜十数MB）をビルド時レンダリングして配信し、他サンプルレート時はリサンプリングして使用する方式
   - ② ブラウザ起動時に毎回2次元異方性板・空気室の数値シミュレーションから直接IRを計算する方式
3. **不採用とした理由**: ①の配信容量膨張とリサンプリング誤差、および②の起動数秒待ちを同時に避け、Pianoteq並みの極小容量と任意レート即時追従を両立するため。
4. **判断誤りの検知シグナル**:
   - M6にて、① 1,000〜2,000モード合成では `4 kHz` 以上の高域拡散残響（modal overlap）密度が不足し金属的・離散ピーク的に響く場合。
   - ② 18経路×0.5秒IRの合成所要時間が `100 ms` を超え、大屋根開閉や視点切替時のUI応答を損なう場合。
5. **事前仕込みとリカバリ移行手順**:
   - **事前仕込み**: `piano-radiator::ir_synth` と `partitioned_fft.rs`（NUPOLS）の間の境界を「時間領域IRスライス渡し」で疎結合に保つ。
   - **移行手順**: ① 高域密度不足時は `piano-body-gen` に高域統計的拡散テール極群を追加するか、圧縮済み高域残響テールIRアセット＋多相FIRリサンプラのハイブリッド読込へ切り替える。② 合成負荷超過時はIR合成を専用 `Web Worker` へ逃がし、`partitioned_fft.rs` のFDL係数をダブルバッファ・クロスフェードで無音切替する。

## D4：8ゾーン×ステレオ出力＋4聴取視点プリセット＋グローバルボイシング編集

1. **現在の採用判断**: 空間出力は8ブリッジゾーン＋1棚板ゾーンのステレオ2ch畳み込み（18経路）に統一し、聴取視点4プリセット（奏者・近接・客席・バイノーラルHRTF）＋大屋根3状態（全開/半開/閉）と主要ボイシング（ハンマー硬度・ユニゾン揺らぎ・ストレッチ調律・弦長）の全体編集を提供する。
2. **今回見送った選択肢**:
   - ① 3D空間内での最大8本仮想マイクの自由配置（座標・指向性可変ミキサー）とマルチチャンネル出力
   - ② 88鍵個別（ノート単位×最大30種）の詳細VoicingエディタUI
3. **不採用とした理由**: Web初期構成における計算経路数（18経路 vs 64経路以上）とUI複雑性を適切に制御するため。
4. **判断誤りの検知シグナル**: M7以降または将来のDAWプラグイン化において、エンジニア向けの自由マイクワーク（リボンマイク近接やサラウンド出力）や、特定鍵のみの整音（単一鍵のハンマー硬化・ユニゾン微調整）が要求された場合。
5. **事前仕込みとリカバリ移行手順**:
   - **事前仕込み**: `piano-spec::voicing` のデータ型を「グローバル基準値 ＋ `NoteVoicingOffset[88]`（初期値ゼロ）」として設計し、`piano-radiator::ir_synth` の視点射影を3D座標・指向性重み関数として抽象化する。
   - **移行手順**: コア物理エンジンを壊さず、出力バス配列の拡張とノート別エディタパネルの追加のみで段階的に機能解放する。

## D5：当面はWebアプリ＋検証用ネイティブCLIのみ実装（単体アプリ・DAWプラグインは将来枠）

1. **現在の採用判断**: コアエンジン（`piano-engine`）はサンプル正確・MIDI 2.0 16bit対応のアロケーションフリーAPIとして設計するが、当面の実装対象はWebアプリ（`apps/web`）とネイティブ検証・ベンチマークCLI（`piano-cli`）に限定する。
2. **今回見送った選択肢**: 初期ロードマップ内での `cpal`＋`midir` ネイティブリアルタイム単体アプリ、または `nih-plug` によるVST3 / CLAPプラグインの同時開発。
3. **不採用とした理由**: ユーザー指示「当面はWebのみの動作で構わない」に従い、ブラウザ実稼働までの最短距離を確保するため。
4. **判断誤りの検知シグナル**: ブラウザ固有の `128` サンプル `AudioWorklet` 量子や Web MIDI のOSドライバジッタにより、超低遅延（`64` サンプル＝`1.33 ms` 以下）でのタッチ追従評価や16bit連続ベロシティ実機検証が阻害される場合。
5. **事前仕込みとリカバリ移行手順**: `piano-engine::render_block(&mut self, events: &[SampleEvent], out_l: &mut [f32], out_r: &mut [f32])` は完全にOS/Web非依存で設計するため、必要になり次第 `crates/piano-standalone`（`cpal`＋`midir`）または `crates/piano-plugin`（`nih-plug`）を約300行規模の新規クレートとして即座に接続する。

## D6：Vanilla TypeScript + Vite によるゼロフレームワークWeb UI

1. **現在の採用判断**: `apps/web` はランタイムGC負荷最小・バンドル最小を優先し、UIフレームワークを使用しないVanilla TypeScript＋Vite構成で白紙から新規実装する。
2. **今回見送った選択肢**: React / Svelte / SolidJS 等の宣言的UIフレームワークの採用。
3. **不採用とした理由**: 演奏中のAudioWorkletコールバックと同一プロセス内のメインスレッド描画GCスパイクを極小化し、500行/ファイル以下の明確なモジュール構造を保つため。
4. **判断誤りの検知シグナル**: M7以降で88鍵個別の物理曲線グラフ編集や複雑なプリセット階層UIが追加され、手動DOM更新コードが1ファイル500行上限下で煩雑化・保守困難になった場合。
5. **事前仕込みとリカバリ移行手順**: `apps/web/src/audio/` および `src/midi/` はDOM APIに一切依存しない純粋TSクラスとして分離しておく。移行時はUI表示層（`src/ui/`）のみを仮想DOMなしコンパイル型フレームワーク（Svelte 5 / SolidJS等）へ局所置換する。

## D7：旧v1 TypeScript製DWG音源・既存UI/E2Eの完全撤去（白紙再設計）

1. **現在の採用判断**: M1において既存のv1 TypeScript製DWG音源・Web UI・テスト基盤には依存せず一掃し、Rust Workspace＋新Webアプリ構成へ置換する。
2. **今回見送った選択肢**: 既存88鍵Web UIやPlaywright基盤の流用、およびWeb画面上での旧TS音源と新Rust音源のリアルタイムA/B聴き比べ機能維持。
3. **不採用とした理由**: 旧コードの設計制約（TS AudioWorklet前提・単一率DWG・旧UIイベント契約）を引きずらず、2層4ステージの新規物理モデルに最適化した構造を最短で組むため。
4. **判断誤りの検知シグナル**: M3〜M6の音量スケーリング、高域減衰バランス、または鍵盤ポインタ操作性の基準確認において、旧v1実装との定量・音響比較が必要になった場合。
5. **事前仕込みとリカバリ移行手順**: M1で旧ファイルを削除する直前に、現行 `main` 先頭（`c75cf57`）へGitタグ **`v0.1.0-ts-dwg`** を打刻して履歴を永久保全する。比較が必要になった際は `git worktree add /tmp/pianosim-v1 v0.1.0-ts-dwg` で旧実装を一時展開し、WAV出力によるオフライン定量比較を随時実施する。

## D8：録音波形を一切使わない純粋物理モデリング単独方式

1. **現在の採用判断**: サンプル波形や録音メカノイズを一切使用せず、楽音から棚板衝撃（keybed thump）までを純粋物理演算で生成する。
2. **今回見送った選択肢**: マルチサンプリング波形または録音された機構ノイズ（鍵盤・ダンパー・ペダル作動音）を併用するハイブリッド方式。
3. **不採用とした理由**: 共有レポートの差別化軸である「連続ダイナミクス・無制限再打弦・極小容量・クリーンルームFTO」を純粋物理で完結させるため。
4. **判断誤りの検知シグナル**: M6〜M8の主観評価において、ダンパーフェルトの離着摩擦音やペダルロッドの作動音など、非楽音メカノイズのリアリティが純粋モードモデルだけでは不足すると判明した場合。
5. **事前仕込みとリカバリ移行手順**: 録音波形やヤマハ特許（`JP7306402B2`：2系統個別減衰制御）に抵触する手法は採らず、`piano-action` 内に鍵速度・ペダル速度を駆動入力とする軽量な物理摩擦ノイズ生成器（数KBの統計的粒子接触モデル）を追加し、既存の棚板／構造体放射ゾーンへ力インパルスとして統合入力する。
